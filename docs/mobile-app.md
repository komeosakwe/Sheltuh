# Phone app (Capacitor)

Status: **Phase 2, increment 1 (the app shell): built, never run on a device.**
Nothing has been built into an APK or an iOS app yet, nothing is signed and
nothing is published. Read this before changing `capacitor.config.ts`,
`android/`, `ios/` or `lib/mobile/`.

The installable web app (Phase 1) is in `docs/pwa.md`.

## Architecture: one codebase

The app is a thin native shell around the live site. Capacitor's WebView
opens `https://sheltuh.com.au/` (`server.url`) and the site runs inside it
exactly as in a browser: same pages, same API, same deploys. There is no
static export (the Next app has server routes and server rendering) and no
second front end. A deploy to Vercel updates the app's content; a store
release is only needed when the native shell changes.

What the shell adds is small, and only inside the app:

| Piece | File | Notes |
| --- | --- | --- |
| Capacitor config | `capacitor.config.ts`, `lib/mobile/app-config.ts` | App id, name, which site to open (`SHELTUH_APP_URL`, production by default), fallback page, system bars. |
| Native projects | `android/`, `ios/` | Generated by `npx cap add` (Capacitor 8.6.2 templates), then: App Links intent filter, backups off, icons. No signing settings, no Apple team. |
| Fallback page | `mobile/www/index.html` | Bundled in the app, shown when the site can't be reached (`server.errorPath`). |
| Native glue | `components/mobile/NativeAppShell.tsx` → `lib/mobile/native-shell.ts` | Deep links and the Android back button. The component is in the root layout but does nothing in a browser; the Capacitor code is a separate ~9 KB chunk fetched only inside the app. |
| App detection | `lib/mobile/native.ts` | `window.Capacitor.isNativePlatform()`, set by Capacitor's native side before the site's scripts run. |
| Deep-link check | `lib/mobile/deep-link.ts` | Only links to the app's own origin, as a same-site path (`lib/safe-next-path.ts`). |
| Verification files | `app/.well-known/assetlinks.json/route.ts`, `app/.well-known/apple-app-site-association/route.ts`, `lib/mobile/well-known.ts` | 404 until configured (see "Deep links"). |
| Icons and splash | `mobile/generate-icons.mjs` | Rerunnable; the ü mark on Signal Orange, as the PWA icons. |
| PWA changes | `lib/pwa/install.ts`, `lib/pwa/service-worker.ts` | Inside the app: no install offer, no service worker. |

**A risk to know about.** Capacitor's own config reference says of
`server.url`: "This is intended for use with live-reload servers. **This is
not intended for use in production.**" The agreed architecture uses it in
production anyway, because a static export isn't possible here. What that
means in practice: the app needs a connection to show anything, it depends on
the live site's availability, and app stores look closely at apps that wrap a
website (see "Store rules"). Increments 2 onwards add native features for that
reason.

## Increment 1: what a person can do

- Install a debug build (once the owner builds one) and use Sheltüh as on the
  phone's browser: browse, search, the map, event pages, Who's Going,
  messaging, buying tickets on the embedded Stripe payment page, the account
  page, the organiser dashboard.
- Signing in with **email and password** works fully inside the app (sign-up
  and password reset use codes typed into the app, not links).
- **Android back** goes back through the pages visited in the app; on the
  first page it leaves the app (moved to the background, as Android 12+ does
  for any app's first screen).
- **Deep links** (once switched on): tapping an event link or the ticket
  email's button opens that page in the app.
- **No connection:** the app shows "Can't reach Sheltüh" instead of a blank
  WebView error.
- The PWA's "add to home screen" offer never shows in the app, and the app
  never registers the service worker.

## What opens where

Only the origin in `server.url` (`https://sheltuh.com.au`) opens inside the
app. There is **no `allowNavigation`**: every other site opens in the system
browser (Capacitor's default; its config docs: "By default, all external URLs
are opened in the external browser").

| Destination | Where | Why |
| --- | --- | --- |
| Every Sheltüh page, `/checkout/pay` included | In the app | Our own origin. |
| Stripe's embedded payment form on `/checkout/pay` | In the app (an iframe) | Iframes aren't navigations. iOS: Capacitor only sends *top-level* navigations out (checked in `WebViewDelegationHandler.swift`). Android: Capacitor's `Bridge.launchIntent` checks every navigation the WebView reports, without a main-frame check; whether Android reports navigations *inside* Stripe's iframe (3-D Secure) is **untested**: see the device checklist. If it breaks, the fix is a small native override that ignores sub-frame navigations (increment 2), not `allowNavigation`. |
| The return from payment (`/checkout/success`) | In the app | Same origin. |
| Supabase sign-in with Google or Apple (`*.supabase.co/auth/v1/authorize`) | System browser | See "Not yet: Google and Apple sign-in". |
| Stripe Connect onboarding for organisers (`connect.stripe.com`) | System browser | Finishes in the browser; the return lands there too. Organisers can complete it on the web. |
| Google and Apple Maps links, external ticket sites, Instagram and other links, "Add to Google Wallet" | System browser / the relevant app | Not ours. |
| `mailto:` and `tel:` links | The phone's mail or phone app | Android: Capacitor starts a VIEW intent for any non-app URL. iOS: untested. |

## Deep links

Android App Links and iOS Universal Links open these addresses in the app
(`APP_LINK_PATHS` in `lib/mobile/well-known.ts`):

| Path | Opens in the app? | Why |
| --- | --- | --- |
| `/events/*/calendar.ics` | No (excluded first) | The phone's calendar should open it. Android 14 and lower can't exclude it (see below). |
| `/events`, `/events/*` | Yes | Event links: what people share and find on Instagram. |
| `/checkout/success` | Yes | The ticket email's "View your tickets" button. The order id in the link is its credential, so it works without signing in, as on the web. |
| `/auth/*` (sign-in return) | **No** | A sign-in started in a browser keeps its one-time PKCE verifier in that browser (`lib/supabase/browser.ts`); if the app caught the return, sign-in would fail in both. Increment 2 adds the app's own return. |
| `/checkout/pay`, `/checkout/confirm`, `/waitlist/*`, everything else | No | They finish where they started; keep the set small. |

In the app, `appUrlOpen` (Capacitor's App plugin) gives the full URL;
`deepLinkPath` accepts it only if its origin is exactly the app's own
(`window.location.origin`) and the path passes `safeNextPath`, then the Next
router shows it. Anything else (another host, a look-alike host, http, a
custom scheme, credentials, `//evil.example` after dot segments) is ignored
and the app stays where it is (`tests/mobile-deep-link.test.ts`,
`tests/mobile-native-shell.test.ts`).

### Verification files: off until configured

| File | Variables (Vercel, Production) | Until set |
| --- | --- | --- |
| `/.well-known/assetlinks.json` | `ANDROID_APP_PACKAGE_NAME` (the app id, `au.com.sheltuh.app`), `ANDROID_APP_CERT_FINGERPRINTS` (SHA-256 fingerprints, comma-separated: Play's app signing key, and the upload or debug key while testing) | 404 |
| `/.well-known/apple-app-site-association` | `IOS_APP_TEAM_ID` (10 characters), `IOS_APP_BUNDLE_ID` (`au.com.sheltuh.app`) | 404 |

Same pattern as wallet passes (`docs/wallet-setup.md`): set the variables,
redeploy, and the file appears; a malformed value keeps it at 404 and the
function log names the variable (never its value). Both are served as
`application/json`, `Cache-Control: public, max-age=3600`, with no redirect.
The values are public by design (anyone can fetch these files), so they don't
need "Sensitive" in Vercel, but don't prefix them with `NEXT_PUBLIC_`.

Android 15+ reads the path rules (and the calendar exclusion) from
`assetlinks.json`; Android 14 and lower use the intent filter in
`android/app/src/main/AndroidManifest.xml` (`/events`, `/events/` prefix,
`/checkout/success`), which can't exclude the calendar file.
`tests/mobile-native-projects.test.ts` keeps the manifest and the path list in
step.

**iOS needs one more step that depends on the Apple team:** the Associated
Domains entitlement (`applinks:sheltuh.com.au`, and `webcredentials:sheltuh.com.au`
for saved passwords) is **not** in the Xcode project yet, because adding it
needs a team and a provisioning profile. Until then Universal Links don't
work on iOS. Steps in "Owner setup: iOS".

**Infrastructure note (for whoever manages the domain):** both files must be
reachable at `https://sheltuh.com.au/.well-known/…` with no redirect. If a
`www.` or other host redirects to or from the apex, links on that host won't
open the app; nothing in `next.config.ts` or `vercel.json` needs changing for
the apex itself (checked with `next start`: 200 when configured, 404 when
not, no `Location` header).

## Caching, storage and offline

Written down before the code, as for the PWA (`docs/pwa.md`).

### No service worker in the app

Inside the app `ServiceWorkerRegistration` never registers `/sw.js`, and
removes any registration and `sheltuh-*` caches (the kill switch's path;
`syncServiceWorker({ nativeApp: true })`). Reasons:

- The app's offline answer is the bundled fallback page, which the native
  shell shows when a page can't load; the service worker's offline page would
  compete with it.
- On older Android WebViews (without document-start scripts) Capacitor injects
  its bridge by intercepting the page request; a page answered by a service
  worker can bypass that (from Capacitor's `Bridge.java` and
  `WebViewLocalServer`; not tested on a device).
- One less cache and update channel to reason about; the app always needs a
  connection anyway.

### What is stored where

| What | Where | For how long | Wiped by |
| --- | --- | --- | --- |
| The fallback page | Inside the app package | Until the next app release | An app update |
| Pages, scripts, images | The WebView's own HTTP cache, following the site's `Cache-Control` headers (as any browser) | As the headers say | The system, clearing the app's storage, uninstalling |
| The Supabase session (sign-in) | The WebView's `localStorage` (existing behaviour, `lib/supabase/browser.ts`), separate from the phone's browser | Until sign-out | Sign out, clearing the app's storage, uninstalling |
| Messages, ticket codes, payment details, Who's Going | **Not stored by the app.** Fetched each time, as on the web | — | — |

Nothing private is added to storage by this increment.

### Storage and backups

- **Android:** `android:allowBackup="false"` and
  `res/xml/data_extraction_rules.xml` exclude every app file (the WebView's
  storage, so the session, included) from Google cloud backups and from
  phone-to-phone transfers. Android's docs: Auto Backup includes
  `getDir()` directories by default, which is where the WebView keeps its
  data. People sign in again on a new phone.
- **iOS:** not addressed yet. iOS device and iCloud backups may include the
  WebView's website data (and so the session) by default (**unverified**).
  Excluding it needs native code; noted for a later increment.
- **A lost, unlocked phone:** the app opens signed in, as the phone's browser
  would. Signing out on the web doesn't sign out the app (separate sessions).

### Offline: what people see

| Situation | What happens |
| --- | --- |
| Opening the app with no connection | "Can't reach Sheltüh": check your connection; close and reopen if it still doesn't load. Ticket QR codes are in the confirmation email. |
| Connection drops on a page | The page stays; anything needing the server shows that screen's existing error. |
| Navigating with no connection | The fallback page. "Try again" appears when there's a page to go back to (`history.back()`), otherwise the close-and-reopen line. Which of the two shows on each platform is untested. |
| Tickets, messages, buying | Need a connection, as on the web. |

## Not yet (later increments)

- **Google sign-in.** Google refuses OAuth sign-in inside embedded WebViews
  (`disallowed_useragent`; already handled for Instagram-style in-app
  browsers in `lib/auth/in-app-browser.ts`). In the app, Supabase's
  authorize URL is another origin, so it opens in the system browser and the
  sign-in would finish there, not in the app. **Plan for increment 2:** open
  the authorize URL in the system's auth session (`ASWebAuthenticationSession`
  on iOS, Custom Tabs on Android), return to an app-only address (an App
  Link / Universal Link path such as `/auth/app-callback`, or a custom
  scheme), and exchange the PKCE code inside the app's WebView, which holds
  the verifier. That needs a **Supabase redirect URL entry** for the app's
  return (docs/supabase-setup.md currently says "no Redirect URLs entries"):
  a backend/owner change, decided in increment 2. **Until then, keep
  `NEXT_PUBLIC_AUTH_PROVIDERS` off, or hide those buttons inside the app**;
  email and password work.
- **Apple sign-in.** Same flow as Google. Apple's guideline 4.8 means that if
  the app offers Google sign-in it must also offer an equivalent such as Sign
  in with Apple. Blocked on the Apple Developer entity decision
  (`docs/PROJECT_CONTEXT.md`).
- **Account deletion inside the app** (Apple 5.1.1(v), below). The account
  page deletes the member profile; deleting the whole account points to the
  Privacy Policy. A self-serve account deletion needs a backend endpoint
  first.
- **Push notifications** (messages, event reminders).
- **Saved tickets offline**: needs an approved design for storing ticket
  codes on the device (expiry, wipe on sign-out, device loss) before any code.
- **Native door scanner.** The web scanner (`/dashboard/[eventId]/check-in`)
  needs the camera; the app declares **no camera permission** (Android) and
  **no `NSCameraUsageDescription`** (iOS) yet, so it won't get the camera in
  the app. Same for "near me" location (no location permission or
  `NSLocationWhenInUseUsageDescription`). Adding them changes the store
  privacy declarations: an owner decision with the scanner increment.
- **Wallet passes in the app**: Apple Wallet's `.pkpass` and the `.ics`
  calendar file are downloads; how the WebView handles them is untested.
- **Splash screen polish**: there's no splash plugin; the system launch screen
  shows, then the WebView's white background until the site paints.
- **Store listings, signing, privacy labels and data safety forms**: owner
  actions, not started.

## Owner setup

Nothing here signs, uploads or publishes. Capacitor's CLI sends anonymous
usage data from interactive terminals; to turn that off on your computer:
`npx cap telemetry off`.

### After cloning or pulling (every platform)

```sh
npm ci
npx cap sync        # copies capacitor.config.ts and mobile/www into android/ and ios/
```

`npx cap sync` regenerates files that aren't committed (the copied config,
the Cordova plugin shims). Run it after any change to `capacitor.config.ts`
or `mobile/www`, and after updating Capacitor packages. It runs no Gradle or
Xcode build on its own. To point a build at another site (a preview
deployment, or `next dev`), set `SHELTUH_APP_URL` for the sync:
PowerShell `$env:SHELTUH_APP_URL="https://preview.example.com"; npx cap sync`,
Git Bash `SHELTUH_APP_URL=http://10.0.2.2:3000 npx cap sync android` (the
Android emulator's address for your computer; plain http is only accepted
for `localhost`, `127.0.0.1` and `10.0.2.2`). Sync again without it before
building anything you'll keep.

### Android: a debug APK on Windows

1. Install **Android Studio** (Capacitor 8 needs Otter 2025.2.1 or newer;
   it includes the JDK). In its SDK Manager, install an Android SDK Platform
   (API 36) and the platform tools.
2. `npx cap sync android`, then `npx cap open android` (or open the
   `android` folder in Android Studio) and let Gradle sync.
3. **Build → Build App Bundle(s) / APK(s) → Build APK(s)**, or in a terminal
   `cd android` then `.\gradlew.bat assembleDebug`. The APK is
   `android\app\build\outputs\apk\debug\app-debug.apk` (ignored by git).
4. Install it: plug in a phone with USB debugging on and press **Run** in
   Android Studio, or `adb install -r app-debug.apk`.
5. Debug builds are signed with your computer's own debug key
   (`%USERPROFILE%\.android\debug.keystore`). To try App Links with it, get its
   fingerprint with
   `keytool -list -v -keystore %USERPROFILE%\.android\debug.keystore -alias androiddebugkey -storepass android -keypass android`
   (the SHA256 line), and set it with the package name in Vercel **Preview**
   for a preview deployment, never Production with a debug key. Release keys
   and Play App Signing come later; never commit a keystore (`.gitignore`
   blocks `*.jks`, `*.keystore`, `*.p12`).

### iOS: needs macOS

Xcode only runs on macOS (Capacitor 8 needs Xcode 26+). The `ios/` project was
generated on Linux with Capacitor's Swift Package Manager template and has
never been opened in Xcode. On a Mac or a cloud macOS runner (a later
increment):

1. `npm ci && npx cap sync ios && npx cap open ios`.
2. Run on a simulator (no Apple account needed).
3. For a phone, Universal Links and any release: once the Apple entity is
   enrolled, in Xcode → the App target → **Signing & Capabilities**: choose
   the team, then **+ Capability → Associated Domains** and add
   `applinks:sheltuh.com.au` and `webcredentials:sheltuh.com.au`. Set
   `IOS_APP_TEAM_ID` and `IOS_APP_BUNDLE_ID` in Vercel and redeploy. Commit
   the entitlements file Xcode creates; never commit certificates or
   provisioning profiles.

### Icons

`node mobile/generate-icons.mjs` redraws every Android and iOS icon and splash
image from `public/brand/sheltuh-u.svg`. Run it after `npx cap add` recreates a
project.

## Store rules we checked (not a promise of approval)

Nothing here means a store will accept the app.

- **Apple 4.2 Minimum Functionality:** "Your app should include features,
  content, and UI that elevate it beyond a repackaged website." 4.2.2: apps
  "shouldn't primarily be … web clippings, content aggregators, or a
  collection of links." A shell that only opens the site is at risk; plan
  native features (push, saved tickets, scanner, native sign-in) before
  submitting.
- **Apple 3.1.3(e) Goods and Services Outside of the App:** "If your app
  enables people to purchase physical goods or services that will be consumed
  outside of the app, you must use purchase methods other than in-app
  purchase". Tickets to in-person events are bought for an event attended
  outside the app, which is why Stripe (not in-app purchase) is used. This
  covers event tickets only: anything digital or used inside the app (for
  example if promoted listings were ever sold in the app) needs its own check.
- **Apple 5.1.1(v) Account Sign-In:** "If your app supports account
  creation, you must also offer account deletion within the app." Not met
  yet (see "Not yet").
- **Apple 4.8 Login Services:** offering Google sign-in requires an
  equivalent option with the listed privacy properties (Sign in with Apple is
  one).
- **Google Play, WebView apps and minimum functionality:** Google's 2020
  developer blog says apps that are mainly WebViews of a website can be
  removed as "webview spam" and flagged under the minimum functionality
  policy. **Unverified:** the current Play policy pages couldn't be read (see
  Sources).
- **Google Play billing for real-world services:** that tickets for physical
  events are outside Google Play's billing requirement is **unverified** here
  (the policy page couldn't be read).

## Real-device test checklist

Send back, for each item: the phone model and OS version, pass/fail, and a
screenshot or a sentence for anything odd. Use a test account and Stripe
**test mode** only (a preview deployment with test keys, built with
`SHELTUH_APP_URL`), never a real card.

**Android (debug APK)**

1. Install and open: the icon (orange, black ü) and the name "Sheltüh" on the
   home screen; the home page loads; the status bar icons are light and
   readable over the black header; nothing hides under the status bar or the
   gesture/navigation bar (top header, bottom buy bar, message composer).
2. Back: open an event, then another page; Back returns step by step; on the
   home page Back leaves the app, and reopening shows where you were.
3. Sign up / sign in with email and password; sign out; sign in again.
4. Buy a ticket with Stripe test card `4242 4242 4242 4242`, then with a 3-D
   Secure test card (`4000 0027 6000 3184`): does the 3-D Secure step stay
   inside the app and complete? Do you land on your tickets page?
5. Messaging: type in the composer with the keyboard open; is the box
   visible?
6. Turn on aeroplane mode, close and reopen the app: the "Can't reach Sheltüh"
   page. Turn it off: does "Try again" (if shown) or reopening work?
7. Tap an external link (an event's Google Maps link, an external ticket
   link): it opens outside the app. A `mailto:` link opens the mail app.
8. "Add to calendar" and "Add to Google Wallet" on a ticket: what happens?
9. Door scanner (as an organiser) and "near me" on the map: expected to fail
   to get the camera/location in this increment. Confirm it fails with a
   message and doesn't crash.
10. Deep links (only once `assetlinks.json` is on for a deployment that
    matches the build): `adb shell pm get-app-links au.com.sheltuh.app`
    shows `verified`; tapping an event link in Gmail opens the app on that
    event; a calendar link doesn't.

**iOS (simulator first, then a phone once signing exists)**

1. Same as Android 1, 3, 4, 5, 6, 7, 8.
2. Door scanner and "near me": expect a denial, **not a crash** (there's no
   `NSCameraUsageDescription` / `NSLocationWhenInUseUsageDescription`).
3. Swipe-back gesture between pages: does it work, or only the site's own
   back links?
4. Universal Links: only after the Associated Domains step; tap an event link
   in Mail or Notes.
